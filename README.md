## supabase/migrations/00000000000000_baseline.sql (17 Sep 2026)

Reflects the escapenfly-crm Supabase project's (`zkhbaisggymbmurqxejk`)
production schema **as of 17 Sep 2026** — tables, constraints, indexes,
functions, views, RLS policies, and grants. Generated by introspecting
`pg_catalog`/`information_schema` directly (a `pg_dump --schema-only`
equivalent), since none existed before and none of the 49 migrations
tracked in this project's own history (`20260801...` onward) actually
built the base schema — those are all incremental changes on top of a
foundation that predates migration tracking entirely.

**Why this exists**: `create_branch()` (both the Supabase MCP tool and
`supabase branches create`) replays a project's tracked migration
history onto a fresh preview branch. Without this file, that replay had
nothing to build the actual tables from — a branch created before this
existed came up with **zero tables**, discovered while setting up a
`maya-tests` branch for the step-6 test-suite work (see PR history).
This file is what makes `create_branch` produce a fully-populated schema
going forward.

**Verified, not just generated**: applied this exact SQL, in the same
statement order as the file, to a disposable throwaway Supabase branch —
zero errors on any of the 51 `CREATE TABLE`, 120 `ALTER TABLE ADD
CONSTRAINT`, 37 `CREATE INDEX`, 3 function, 1 view, 4 `ENABLE ROW LEVEL
SECURITY`, or 22 `CREATE POLICY` statements — then cross-checked object
counts directly against production: both sides came back identical (51
tables / 120 constraints / 103 indexes / 22 policies / 1 view). That
throwaway branch was deleted after. **Not applied to production itself**
— every table in this file already exists there, so running it as-is
against prod would fail immediately with "relation already exists" on
the first `CREATE TABLE`. That was intentional, per the read-only
scope of this task.

**One manual step still needed, separate from this PR**: merging this
PR gets the file into the repo, but Supabase's branch-replay reads its
own tracked migration history for the project, not files sitting in a
GitHub repo by themselves. For `create_branch` to actually pick this up
on the *next* branch it creates, someone with the Supabase CLI needs to
either run the project's normal migration-deploy flow, or (since every
object in this file already exists in prod) mark it as already-applied
without re-running the DDL — `supabase migration repair
00000000000000 --status applied` against the linked project is the
standard way to do that. Until that happens, `create_branch` still
replays the same (effectively empty, pre-17-Sep-2026) history it always
has.

**Two things reproduced deliberately, not fixed**: (1) several tables
(`activity_log`, `bookings`, `customers`, `enquiries`, `team_members`,
and others — see the migration's own comment above the `CREATE POLICY`
block) carry an `anon_all` policy while their `ENABLE ROW LEVEL
SECURITY` was never actually run — those policies are currently dormant
in production, not doing anything, same shape as the `portal_credentials`
dormant-policy incident CLAUDE.md documents being found and fixed on 18
Aug 2026. (2) grants are close to uniform full-CRUD to
`anon`/`authenticated`/`service_role` on every table, with two known
exceptions: `costing_audits` (RLS-gated, anon/authenticated read-only)
and 6 tables where anon's `DELETE`/`TRUNCATE` were revoked on 28 Aug
2026 (`exchange_rates`, `markup_defaults`, `packages`,
`quote_categories`, `rate_cards`, `visa_intelligence`). This migration's
job was to mirror production exactly as it stands, not to clean it up —
flagging both here since they're easy to mistake for bugs in the
migration itself rather than accurate reflections of prod.

## cron-job.org setup

This service is deployed on Render; cron-job.org is the external scheduler
that hits its `/cron/*` and some `/internal/*` endpoints on a timer (Render's
own Cron Jobs feature isn't used for these — check Render's dashboard
directly if that ever changes).

Every job below sends the shared secret either as `?secret=...` or the
route's own header (see each route's auth function in `server.js`) —
`CRON_SECRET` for `/cron/*` routes, `ADMIN_WRITE_SECRET` for the two
`/internal/*` ones listed here.

### New (16 Sept 2026) — publish-social.js

| Time (IST) | Method | URL | Secret |
|---|---|---|---|
| 09:20 daily | POST | `/internal/team-daily-content` | `ADMIN_WRITE_SECRET` |
| 09:30 daily | POST | `/cron/fb-safety-crosspost` | `CRON_SECRET` |

- **09:20 `team-daily-content`** — runs after Cowork's 09:00 Windsor.ai
  posting run so the WhatsApp message carries today's already-live links.
  Sends every active team member (`team_members.is_active` with a non-null
  `phone`) one AiSensy template message with today's content. Test a single
  number first with `?to=<phone>&dry=1`, then `?to=<phone>` for a real send,
  before ever removing `?dry=1` from the scheduled job.
- **09:30 `fb-safety-crosspost`** — the everyday path is Cowork calling
  `/internal/publish-fb?publish_id=...` itself right after each row posts;
  this cron only catches rows that fell through (Cowork skipped or failed
  the call). It finds today's `marketing_publishes` rows with an `ig:` id
  and no `fb:` id yet and cross-posts each one, capped at
  `PUBLISH_MAX_PER_RUN` (env var, defaults to 20) per run.

Both were verified locally against real production Supabase data with
`?dry=1` (see the PR description for the exact commands and output) — not
yet verified against real Meta/AiSensy credentials, which don't exist in
this environment. Do that with Vineet once this deploys, the same way the
Meta/Google sync endpoints above were signed off.
